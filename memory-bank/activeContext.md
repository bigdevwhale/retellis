## Joint family session — fifth fix: the auth race + the missing refetch (2026-07-24)

The "can't see other members' messages in the joint family chat" bug (4th report) survived all four prior fixes because they made the ONE-TIME load correct but left two client defects that dominate real usage:

1. **Auth-bootstrap race.** `app/chat/page.tsx` renders `<ChatScreen>` immediately (server-side cookie check only), so ChatScreen's mount effects fired `hydrateConvos()` / `loadConvoMessages()` while `AuthProvider`'s bootstrap was still awaiting `getAuthConfig → getMe → loadFamily`. With `family`/`myUserId` still null the joint convo loaded WITHOUT the family shared filter (server then excludes other members' rows by ownership) — and the wrong result stuck for the whole session via the load-once guard (or seeded the greeting over an empty result). `hydrateConvos` likewise skipped the shared-scope sidebar merge. Fix: both effects now wait for `!authLoading` (the bootstrap awaits `loadFamily` before flipping `loading` false).
2. **No refetch, ever.** `loadConvoMessages` guarded `msgs.length > 0 → return` — once the joint thread had ANY local messages, messages other members sent later were never fetched (no poll, no focus/activate refetch; only a full page reload helped). Fix: `loadConvoMessages(convoId, { force: true })` bypasses the guard and wholesale-replaces from the server (a forced EMPTY result never wipes local messages — post-stream `_after_done` persist lag). ChatScreen runs a joint-thread refresh while a `fam-joint-` convo is active: immediate on activation + on window focus + an 8s poll (visible tab only), skipping in-flight turns (`sendingRef`/`streaming`/`typing`) and a 4s post-send cooldown (`lastSendAtRef`, set in send()'s `finally` and `stop()`). Effect deps are stable primitives (`jointActiveCid` string) — NOT `convo` — because each refresh replaces the convos array and an object dep would loop the network.

Files: `apps/web/lib/store.ts` (force param + empty-guard), `apps/web/components/screens/ChatScreen.tsx` (auth gating ×2, refresh effect, `JOINT_POLL_MS=8000`/`JOINT_SEND_COOLDOWN_MS=4000`, `lastSendAtRef`). Tests: `apps/web/tests/conversations-hydration.test.ts` — new `loadConvoMessages force refresh` describe (force bypasses the guard + picks up the other member's new message with the shared filter; forced empty result keeps local messages). 181 web green (30 files); tsc + biome clean. Server untouched (already proven by `test_joint_visibility_http.py`). **Lesson:** all four prior fixes verified the load path in isolation; the bug lived in WHEN the load runs (before the family slice exists) and WHETHER it ever runs again (it didn't).

## Joint family session — fourth fix: the ACTUAL root cause (2026-07-24)

The "can't see other members' messages in the joint family chat" bug (reported 3×) was **client-side, not server-side**. The send path read the family SCOPE (`visibility`) from the separately-toggleable `familySessionMode` store field, while the load path derived visibility from the convo id (`convoFamilyVisibility`). `openConvo` (sidebar click) + `hydrateConvos` set `activeConvoId` but **never synced `familySessionMode`**, so opening an existing `fam-joint-` convo left `familySessionMode` at its default `'private'` → the send stored the member's message as **private under the joint convo id** → the other member's shared-scope load returned shared events only → saw nothing. The server was correct end-to-end, proven by the new `apps/api/tests/test_joint_visibility_http.py` (A sends shared via `POST /v1/llm/stream`, B reads `GET /v1/memory?family_id=&visibility=shared&participant_user_id=` and sees A's message attributed to A; B's joint read excludes A's private solo). Fix (3 files): `apps/web/components/screens/ChatScreen.tsx` send path now derives `visibility` from `convoFamilyVisibility(cid)` (ground truth — the convo it persists into and the load reads), falling back to `familySessionMode` only for legacy non-prefixed fam convos; `participant_user_id` is forced to the principal (`myUserId`) in joint mode (server requires participant==principal; picker disabled in joint); `apps/web/lib/store.ts` `openConvo` + `hydrateConvos` sync `familySessionMode` to the opened convo (`fam-joint-`→shared, `fam-solo-`→private, non-fam untouched). Tests: `apps/web/tests/joint-visibility-sync.test.ts` (openConvo sync ×3 + send-derives-visibility ×2, incl. the exact desync case `familySessionMode='private'`+`activeConvoId='fam-joint-'`→body `visibility='shared'`); `apps/api/tests/test_joint_visibility_http.py` (2 HTTP integration tests). 179 web + 27 api green; tsc + biome + contracts:check clean. **Lesson:** the store-level `test_joint_shared_visible_to_other_member` passed throughout but never exercised the HTTP/router layer or the web send path — the bug lived in the glue the store test bypassed.

## Joint family session — shared cross-member visibility fixed (2026-07-24)

In a joint (`familySessionMode='shared'`) `fam` session members only saw their own messages and the therapist's LLM context only contained the speaker's history. Three causes, fixed together:

1. **`convo_id` was minted per-member** (`apps/web/lib/store.ts::newChat`). Now `newChat('fam')` in shared mode returns a deterministic `fam-joint-{family.id}` via the new `familyJointConvoId` helper, with create-or-reuse (no duplicate stub). The Solo/Joint toggle in `apps/web/components/screens/ChatScreen.tsx` now moves the active convo to match the mode (Joint → the shared convo; Solo → a fresh solo convo only if currently on the joint one). `convoFamilyVisibility(convoId)` derives `shared`/`private`/`null` from the `fam-joint-`/`fam-solo-` prefix.
2. **Server pre-filtered `user_id == requester` before the family-scope predicate** (`apps/api/.../memory/store.py`). `_apply_family_scope` already admitted any member's shared row in family `F`, but the ownership filter dropped other members' rows first. New `_owns_or_shared` helper (InMemory) + an `or_(user_id == me, family_id == F AND visibility == shared)` ownership predicate (Postgres) relax the filter **only** for `visibility=='shared'` in `list_events`/`recent_window`/`list_conversations`/`recall_candidates` (both stores). Private/solo stays strictly `user_id`+`participant_user_id`-gated; `family_id` is still pinned to the requester's family by `_require_family_match`/`_validate_family_scope`, so the relaxation can't leak another family's events. `_events_to_window` attribution was already correct.
3. **Client never passed family scope to `listEvents`**. `loadConvoMessages` now passes `familyFilter` for joint convos; `hydrateConvos` issues a second `listConversations` call for the family shared scope (when `family` present) and merges/dedupes by `convo_id` so the joint convo is in every member's sidebar. New `myUserId` store field (set by `loadFamily`) supplies `participant_user_id`. `listConversations` (api-client) gained an optional `familyFilter`.

No contract change (convo_id isn't on the wire; family scope params already exist). Tests: new `test_joint_shared_visible_to_other_member` in `apps/api/tests/test_family_recall.py`; web `family-store.test.ts` deterministic+create-or-reuse assertion + `conversations-hydration.test.ts` `loadConvoMessages` familyFilter cases. 572 api + 168 web green; contracts 45-model parity; ruff+tsc+biome clean; `grep -r 'sk-' deploy/` empty.
